## Implemented API and source authority

- backend/security/firebase_auth.py::firebase_admin_principal/get_admin_principal resolve stable verified subjects. Existing is_firebase_admin_token and verify_admin_credentials boolean/key interfaces remain. Cache holds only token fingerprints, expiry, allowed email and stable principal; allowlist is rechecked on cache hits. Invalid/expired/nonfinite/bool/overflow expiration or malformed SDK returns fail closed.
- backend/core/conversation_sessions.py::save_conversation/read_conversation/list_conversations stores full canonical message JSON/title with SHA256, IDs, expected revision, count and timestamp. Two private tables, conversation_heads and conversation_revisions, are created only by a valid admitted write in the existing vault transaction. BEGIN IMMEDIATE and compare-and-swap serialize writers. Independent committed readback confirms a revision before durable=True. Existing global archive rows remain unchanged. Revisions are immutable through this API; there is no pruning/delete endpoint.
- backend/routers/conversation_router.py is included by existing memory_router.py, whose /api/memory prefix produces GET /conversations/identity, GET /conversations (limit1-50 and optional before cursor), GET /conversations/{32hexID} (optional revision), and POST /conversations/{32hexID}. POST body is request_id, expected_revision, messages and title; additional owner/client fields reject. Each message must carry a unique32hex id, with the remaining finite JSON metadata retained. The owner always comes from backend credentials. No configured DB path is accepted from the client.
- List order/cursor is descending stable conversation ID, not last-edited order or a frozen multi-page snapshot. Missing tables mean empty new history only when neither private table exists; incomplete schema or missing/corrupt recorded revisions fail rather than report empty success. Errors map to403/404/409/422/503 as applicable and never return a database path. Reads do not initialize schema. Missing vault files are never created.

## Browser storage stage, v5.329.32

frontend/src/utils/conversationOutbox.js::openConversationOutbox opens a dedicated IndexedDB outbox only when explicitly called. This is a pending-write journal for the authoritative existing SQLite service, not another server memory/vector store. Two stores, heads and entries, key all local conversations by normalized backend URL, verified-owner label and conversation ID. Only queueSnapshot/prepareNext/acknowledge/markConflict/closeConversation mutate it; loadConversation/listConversations read, close releases the connection. No HTTP, app-state mutation, credentials, background worker or deletion occurs in this module. Its owner argument is scope metadata, not authentication: the integration must obtain it from the protected backend identity endpoint. Same-origin scripts/browser-profile access can read IndexedDB; this is not encryption or protection against a compromised origin/profile.

queueSnapshot atomically checks expectedLocalRevision and writes full finite plain-JSON messages/title plus local SHA256. It rejects duplicate message IDs, sparse/unsupported/nonfinite/invalid-Unicode input and payloads over16MiB before storing a head, without trimming. Each entry keeps a stable32hex request ID and local revision; changed ID reuse/conflicting writers reject, exact retry deduplicates. The first queue can seed baseServerRevision from an authenticated server read; subsequent entries use that head's confirmed state. Acknowledged and closed sources remain stored. No automatic pruning or storage-quota guarantee is implied.

prepareNext freezes one request body/base revision before returning it. Network loss/restart can reuse that exact request ID/body; later edits queue separately. acknowledge validates the server receipt's identifiers/revision/count/durable/storage/hash shape, rechecks unchanged local source and advances exactly once/in order. The local source hash and server canonical payload hash are different formats; receipt validation here is not independent proof of server contents or authentication. The backend still performs its own exact committed readback, and future transport must confirm selected identity/target and complete returned evidence. Conflict marking retains pending/newer edits and stops automatic advancement. closeConversation marks a view session closed without deleting source or cancelling unsent entries; it does not mean a server/archive save succeeded.

IDB transactions request strict durability, have a10-second deadline and resolve only at transaction completion. Opening has a5-second deadline and rejects missing/blocked storage, without a memory-only fallback. Unsupported durability APIs must fail visibly instead of silently changing the guarantee. These bounds and an actual browser-process restart are not power-loss/hardware/fsync proofs. Browser/platform eviction, private-mode limits and quota failures remain possible; the UI must preserve visible/draft content and never claim a failed local save completed.
