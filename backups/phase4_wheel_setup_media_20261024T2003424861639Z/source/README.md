# AI-BS Offline Wheel Setup v1

This source builds a native x64 .NET Framework GUI that installs only the two approved wheels into the existing current guest user's Python 3.13.17 x64 interpreter. The operator manually opens `D:\AI-BS Wheel Setup.exe` in the dedicated offline VM and chooses the single Install action. This tree contains no launch, attach, autorun, remote command, bootstrap, elevation or task-admission mechanism.

The production entry checks the actual account SID, medium integrity, VirtualBox manufacturer/model, exact VM UUID and zero enabled guest NICs before showing a GUI, invoking Python or writing application state. Its only optional argument is `--check-identity`; other arguments exit 64. The real host and other guests exit 2 without showing a GUI. An embedded Win32 manifest explicitly sets `asInvoker` and `uiAccess=false`.

The helper fixes the interpreter to `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`, verifies its executable, prefix, base prefix, site-package paths, version and bitness, and checks imports and package versions. It rejects linked paths. It requires D: to be a CD-ROM with label `AIBS_WHEELS_V1` and exactly the helper, two pinned wheels, README and manifest. Read handles remain held across the attempt.

Pip is used only if both imports and versions do not already match. Pip must already exist. Its child environment removes pip/Python override variables, fixes `PIP_CONFIG_FILE` to lowercase `nul`, and requires a preflight comparison to the exact `os.devnull` plus an empty effective isolated configuration. No configuration values or environment contents are reported. The native process uses `-I -B` and fixed isolated/no-index/no-deps/no-cache/no-compile arguments with the two fixed local wheel paths. There is no `--user`, alternative interpreter or pip bootstrap.

One exclusive lease and a flushed exclusive intent precede native probes and pip mutation under `%LOCALAPPDATA%\AI-BS\OfflineWheelSetup\v1`. Any retained intent, including an interrupted, failed or corrupt one, blocks replay. Each process has a monotonic deadline and combined output-byte limit; an overall monotonic budget bounds starting/running processes. An uncertain result is quarantined. Killing a client is not proof that descendants were contained or stopped. Package verification grants no task authority or Phase 4 acceptance.

Every bounded native result is flushed into a new exclusive local step JSON file before the workflow progresses. It retains the numeric exit code and whether it is known, bounded stdout/stderr, captured bytes, cap/deadline/elapsed facts and timeout/cancellation flags. There are at most six step records with a 128 KiB serialized bound each. Raw guest output remains local; no configuration/environment dump is requested. The ordinary GUI path returns zero only for a final VERIFIED result. Closing before Install or after an unverified, failed or cancelled attempt returns nonzero. The explicit identity-check-only mode reports only the guard result.

Cancellation requests and the flushed VERIFIED commit use one shared atomic completion boundary. A cancellation accepted first prevents the shared production success commit from writing VERIFIED and yields quarantine/nonzero. If the durable commit acquires the boundary first, it flushes VERIFIED and records the final outcome before a later close can acquire the boundary; that close is completed-before-cancel and is not accepted as cancellation. Both already-matching and post-install success paths use the same commit function. Focused tests cover cancellation first, commit first, and overlapping threads around an actual flushed result.

Path reparse checks and held read handles narrow file replacement risks but do not prove containment against adversarial directory replacement races. This helper and its process termination are not task isolation or descendant-containment proofs.

`Build-Test-WheelSetup.ps1` uses the installed x64 .NET Framework compiler. It requires a fresh `build` directory and runs only trusted infrastructure fixtures, resource-only manifest extraction, and actual host-refusal entry checks. It never runs Python, pip, Node or an installer as a host runtime probe. `WheelStagedManifestTests.cs` separately validates real staged JSON and file hashes through the production parser without entering the production application.

`Build-WheelMedia.ps1` packages into a fresh timestamped backup folder using native IMAPI CreateNew output. It independently pins the complete retained original ISO, extracts only the two approved wheel extents, checks all staged hashes, preserves read handles and uses only new output files. It adds only the worker's ReadAndExecute permission if an adequate inherited rule is absent, preserving existing sufficient inheritance. `Verify-WheelISO.py` independently reads complete ISO9660/Joliet directories, path tables, extents and all five payloads without mounting the image. `Test-WheelISO.py` exercises parser rejection and valid IMAPI representations.

Primary pip evidence: [configuration documentation](https://pip.pypa.io/en/stable/topics/configuration/#pip-config-file) and [configuration source](https://github.com/pypa/pip/blob/main/src/pip/_internal/configuration.py). The guest preflight verifies the installed pip's actual effective behavior; no pip version or source compatibility is assumed.

The GUI, pip invocation and post-install verification have not been exercised in the guest. Independent source review and a deliberate human launch remain required. Originals, prior failed build folders and retained attempt history are preserved.
