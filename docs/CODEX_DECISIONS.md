## ADR-001: Three-Layer Persistent Engineering Memory & Lifecycle Hook Architecture
- **Date:** 2026-10-24
- **Status:** Active / Verified on Codex `v0.164.0-alpha.11.1` (`windows-x86_64`)
- **Context:** Long-running autonomous development across Phases 1–6 experiences context compaction and session restarts. Relying on conversation history alone risks losing checkpoint paths, hash invariants, runtime PID/flag baselines, and deferred scope boundaries.
- **Decision:**
  1. Maintain durable repository truth across:
     - `AGENTS.md` (and `C:\Users\footb\.codex\AGENTS.md`) — Permanent operational instructions and safety invariants.
     - `docs/CODEX_HANDOFF.md` — Authoritative current engineering state and versioned checkpoint records.
     - `docs/CODEX_JOURNAL.md` — Append-only chronological history of checkpoints, lifecycle hook triggers (`SessionStart`, `PreCompact`, `PostCompact`, `Stop`), test results, and diagnostic halts.
     - `docs/CODEX_DECISIONS.md` — Architectural decisions and rationale.
     - `docs/CODEX_TASKS.md` — Outstanding tasks, dependencies, and acceptance criteria.
  2. Configure native Codex `v0.164.0-alpha.11.1` lifecycle hooks in `C:\Users\footb\.codex\hooks.json` (UTF-8 without BOM) with trusted content hashes in `C:\Users\footb\.codex\config.toml` (`[hooks.state.'...']`) invoking `C:\Users\footb\.codex\scripts\codex_lifecycle_hook.py`.
  3. **Non-Interference Invariant:** Hook scripts read `docs/CODEX_HANDOFF.md`, `docs/AI_BS_Autonomy_Implementation_Plan.md`, `docs/engineering_ledger/2026-10-24_Codex_Engineering_Ledger.md`, and `docs/engineering_ledger/cloud_index.json` strictly in **read-only** mode so they never invalidate an in-flight `before_manifest.json` SHA-256 guard during active checkpoint finalization. Hook checkpoints write atomically to `docs/CODEX_JOURNAL.md`, `docs/CODEX_TASKS.md`, and `C:\AI-BS\backups\codex_hook_checkpoints\`.

Handlers must read raw response text via `res.text()`, safely attempt JSON parsing, and fall back to local `FileReader` data staging for text, code, and image files whenever the backend is unreachable or returns a non-200 status. Server-side upload handlers (`chat_attach_file` in `AI_BS_Backend.py`) must sanitize incoming filenames using `os.path.basename` to prevent Windows path traversal (`C:\fakepath`, `..\..\`) and employ multi-tier text decoding (UTF-8 primary, Latin-1 fallback with `errors="replace"`) to prevent unhandled `UnicodeDecodeError` crashes on non-strict text payloads. 4-mirror frontend parity must be maintained with 100% SHA-256 byte parity.



## ADR-107 - Administrative Bounded Trusted Host Execution Authorization & Strict VM Fail-Closed Policy - 2026-10-28T04:21:00Z
Context:
The candidate coding execution subsystem previously had no mechanism to authorize bounded local test execution on the host when developers or operators wished to test candidates under bounded Windows Job Object containment without an active VM worker. At the same time, AI-BS architectural rules dictate that when an isolated execution environment (windows_vm) is explicitly requested, it must fail closed if the isolated environment is unprovisioned or unavailable; silent substitution or fallback to host checks is strictly forbidden.
Decision:
1. Introduce explicit administrative authorization via environment variables: AI_BS_ALLOW_TRUSTED_HOST_EXECUTION=true and AI_BS_EXECUTION_BACKEND=trusted_host in both root .env and ackend/.env.
2. In ackend/core/coding_workflow.py and ackend/core/coding_chat.py, conditionally permit trusted host execution through bounded Windows process containment (coding_process.run_bounded_check) ONLY when execution_backend == 'trusted_host' and explicitly authorized by administrator policy.
3. Strict Fail-Closed Rule for windows_vm: Whenever execution_backend == 'windows_vm' is requested and AI_BS_VM_ENABLED is not active, the system immediately fails closed with ISOLATION_UNAVAILABLE. Host fallback is strictly forbidden.
4. Protect snapshot integrity: The ~90 GB VirtualBox disk chain (AI-BS-Eval-Base-20261023) remains preserved intact on disk as an offline managed unit, pending isolated containment profile sanitization (disabling NAT, clipboard, and drag-and-drop) and full guest acceptance testing.


## ADR-108 - Dual-Provider Isolated VM Guest Runner (`wsl2_isolated` & `vbox_windows`) with Zero Host Fallback and Transparent Provenance - 2026-10-28T09:10:00Z
- **Requirement / Architecture Identifier:** `AI-BS-UADP-1.0` Section III & Phase 4 Isolated Candidate Execution (`ADR-108`, superseding the hardcoded `ISOLATION_UNAVAILABLE` stub in `ADR-107` while preserving `ADR-107`'s strict prohibition on host fallback).

The original Phase 4 plan contemplated only a disposable Windows 11 guest VM, while treating WSL2 alone (default shared `/mnt/c` + shared network + Windows `.exe` interop) as insufficient without containment hardening.
- **Proposed Change:** Connect a dual-provider hardware-virtualized guest execution module (`backend/core/coding_guest_runner.py`) supporting:
  1. `vbox_windows` (`execution_mode='windows_vm'`): Headless VirtualBox Windows 11 guest via `VBoxManage guestcontrol` against a clean snapshot with `nic1..8=none`, `clipboard=disabled`, `draganddrop=disabled`, zero shared folders, and DPAPI-encrypted guest credentials (`saved_data/vm_runner_config/`).
  2. `wsl2_isolated` (`execution_mode='wsl2_vm'`): Hyper-V / WSL2 Linux utility VM (`Ubuntu-24.04`) hardened per invocation with unshared `CLONE_NEWNS`, `CLONE_NEWNET`, `CLONE_NEWIPC`, `CLONE_NEWUTS`, and `CLONE_NEWPID` (`--mount-proc --propagation private`), empty read-only `tmpfs` masking over `/mnt`, `/run`, `/home`, `/root`, `/media`, `/srv`, `/opt`, and `/proc/sys/fs/binfmt_misc`, ephemeral RAM `tmpfs` `/tmp`, root-owned `0o444` immutable verification files under sticky-bit `0o1777` workdir, `setpriv` drop to `65534:65534` (`nobody:nogroup`) with zero capabilities and `--no-new-privs`, `prlimit` + GNU `timeout -s KILL` resource bounds, and an `x86_64` kernel `seccomp-bpf` filter blocking `AF_VSOCK`, `AF_INET`, `AF_INET6`, `AF_NETLINK`, and `AF_PACKET` while allowing `AF_UNIX`.
  3. Operator-authorized policy flags (`AI_BS_EXECUTION_BACKEND=wsl2_vm`, `AI_BS_ALLOW_WSL2_ISOLATED_VM=true`, `AI_BS_ALLOW_VBOX_WINDOWS_VM=true`, `AI_BS_ALLOW_WSL2_GUEST_FOR_WINDOWS_VM=true`, `AI_BS_REQUIRE_STRICT_WINDOWS_KERNEL_FOR_WINDOWS_VM=false`) allow immediate isolated VM guest execution without failing closed while `vbox_windows` awaits interactive operator password enrollment (`verify_and_connect_guest_runner.py enroll-vbox`), while recording honest runtime provenance (`requested_execution_backend` vs actual `execution_mode` and `guest_provider`) and **never** falling back to `coding_process.run_bounded_check` on the Windows host.
- **Technical Justification:** Windows 11 Home lacks native Windows Sandbox, and the preserved VirtualBox Windows 11 evaluation guest (`AI-BS-Eval-Base-20261023`) requires private local account credential enrollment before `VBoxManage guestcontrol` can authenticate. Meanwhile, Microsoft's Hyper-V lightweight VM (`Ubuntu-24.04`) is active on the host and, when stripped of `/mnt` drvfs mounts, `/run/WSL` interop sockets, capabilities, and `AF_INET`/`AF_INET6`/`AF_VSOCK` syscalls inside ephemeral kernel namespaces, provides true hardware-VM + kernel-sandbox containment for pure Python verification checks today with zero host exposure.
- **Affected Components:** `backend/core/coding_guest_runner.py`, `backend/core/coding_workflow.py`, `backend/core/coding_chat.py`, `backend/core/coding_review.py`, `backend/core/hybrid_reasoning_engine.py`, `backend/core/optional_web_search.py`, `backend/AI_BS_Backend.py`, `backend/routers/chat_router.py`, `backend/tools/tool_registry.py`, `frontend/src/components/CodingTaskReviewCard.jsx` (4 mirrors), `scripts/verify_and_connect_guest_runner.py`, `scripts/tests/test_coding_guest_runner.py`, `scripts/agent_sync/sync_gateway.py`, `.env`, `backend/.env`.

  - Provenance is never conflated: checks executed by `wsl2_isolated` always record `execution_mode: "wsl2_vm"` and `guest_provider: "wsl2_isolated"` in `result.json`, `review_seal` (schema version 2), and `CodingTaskReviewCard.jsx`—never claiming Windows-kernel execution unless `vbox_windows` actually ran. Therefore, Windows-specific OS/Win32 candidate code still requires `vbox_windows` enrollment, and Phase 4 Windows-kernel-specific acceptance remains distinct from `wsl2_vm` Python guest acceptance.

  2. 7-test Number Summary canary passes end-to-end (`VERIFIED` -> `review_task` -> `apply_task` `APPLIED`) with `coding_workflow.run_bounded_check` mocked to raise `AssertionError` (proving zero host execution).
  3. Strict fail-closed tests confirm `ISOLATION_UNAVAILABLE` when `AI_BS_REQUIRE_STRICT_WINDOWS_KERNEL_FOR_WINDOWS_VM=true` and `vbox_windows` is un-enrolled.
