## Fit with AI-BS

The proposal fits the requested broad plain-English task layer and existing admitted coding workflow. Use it to structure observable task state and concise decision summaries: understand a goal, establish constraints, select a plan, check evidence and produce an answer/artifact. Reuse existing task IDs, request journals, permission boundaries and verification evidence. Do not confuse a structured progress record with disclosure or measurement of a model's private internal reasoning.

Reasoning archetypes can be optional, overlapping routing labels: rule checking, diagnosis, constraint satisfaction, trade-off comparison, forecasting and premise checking. They are not mutually exclusive cognitive modes or proof that selecting a label improves a model. Some constraint systems have multiple/no solutions; optimization needs an explicit objective beyond finding a feasible assignment. Predictions and diagnoses should retain uncertainty until evidence distinguishes them.

## Observable five-stage contract

1. **Intent and routing:** distinguish direct answers, idea exploration, requests for a plan and authorized actions. A clear small question gets a direct answer, not a forced interview or expensive multi-pass run. Route by actual needs and available tools; do not label every diagnostic or migration high compute automatically.
2. **Constraint pinning:** record confirmed objective, sources, assumptions, scope, repository/data identity, permissions, bounds and success criteria. Apply the latest explicit user correction over earlier defaults. Ask focused questions only when materially missing information prevents a correct/safe result; preserve settled answers.
3. **Plan and alternatives:** produce a concise proposed approach, necessary dependencies and reversible steps. Distinguish hypotheses from verified faults. Model-generated plans are not execution authority. Respect current VM deferral and fail closed if a requested isolated provider is unavailable.
4. **Verification:** run the admitted, domain-appropriate checks and retain actual evidence/failures. Fixed tests/lockfiles, output/time/cancellation limits and immutable originals remain required. Missing evidence is not success; unsuccessful checks cannot be replaced by persuasive narrative. High-stakes/current domain claims need appropriate primary-source verification when used.
5. **Emission and learning record:** answer clearly or return a reviewable artifact with relevant checks, assumptions, limitations and next steps. Save concise decisions, attempts, tool/test results and outcomes in the engineering ledger. Curate authorized facts/preferences/examples with provenance; do not treat every historical model explanation or hypothesis as a verified training target.

## Corrections before turning examples into acceptance fixtures

- **504 diagnostic example:** low application CPU/RAM and a daily timeout window do not uniquely establish a database lock. Retain scheduled maintenance, pool waits, upstream/network events and other dependency hypotheses until timestamps/traces/lock/pool evidence distinguishes them. The requested diagnostic command must match the actual database/runtime. Avoid declaring a guessed cause confirmed.
- **Name-splitting migration:** the proposed output uses VARCHAR(100), conflicting with the requested VARCHAR(50) fields. Names do not by themselves establish an unambiguous first/last-name mapping. Empty surname handling and accepted field sizes need a business decision. Database engine/version and deployment write paths are needed before promising zero downtime or online constraint behavior. Preserve full_name/original bytes and reconcile any loss before contraction.
- **Contract example:** the two excerpts have an apparent overlapping-retention conflict, but their supplied context does not establish governing definitions, exceptions, precedence or legal retention requirements. A drafting suggestion should be labeled and verified against the complete governing material; it is not a verified legal-compliance outcome.
- **Upload example:** removing shell interpolation is a useful direction, but the displayed command is not validated against the installed conversion tool/Windows runtime. The snippet has no explicit execution timeout, input/resource limit or isolation. A UUID4 is random rather than deterministic. Validate decoder inputs/output containment and actual argument behavior before adopting this as a passing security patch. Never execute the destructive example payload on the host.
- **Compression example:** state the guarantee and data assumptions precisely. Uniform random data is overwhelmingly unlikely to have the proposed reduction; counting arguments rule out such a guarantee for all inputs, rather than proving every individual file cannot compress. A known reproducible generator/seed can be a compact description, but an unknown seed is not a compression result. Keep GB/GiB and MB/MiB consistent.
- **Zero-knowledge example:** the supplied Sigma-protocol outline is one explanatory family, not a complete definition of every ZK system. Perfect completeness and a blanket Fiat-Shamir conversion should not be assumed universally. A primary paper defines completeness with an error parameter, rather than requiring zero error in every system; the current Sigma draft specifies protocol-specific extraction assumptions. See [Watrous, section 2.1](https://cs.uwaterloo.ca/~watrous/Papers/ZeroKnowledgeAgainstQuantum.pdf) and [IRTF Sigma Protocols draft 03, section 7](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-sigma-protocols-03). The latter is work in progress, not an adopted standard. Verify the intended concrete protocol before treating its examples as training/evaluation ground truth.

## Implementation sequence and pass criteria

First complete the current memory access/save reliability work. Then reuse the admitted request model for a bounded task-specification layer: goal, confirmed constraints, assumptions, required clarification, proposed actions, fixed checks and status/evidence references. Preserve raw source/reference copies separately from curated reasoning examples. No new execution path or trainer is authorized by a taxonomy label.

Acceptance examples should include a direct question answered without execution, a broad idea clarified without invented requirements, a latest-user-override case, a diagnostic kept hypothetical pending evidence, a contradictory constraint surfaced plainly, a proposed unsafe action blocked by backend policy, and a failed test reported honestly with no false success. Measure correctness, unnecessary clarification/tool calls, time/usage, preservation and evidence quality. Do not claim Antigravity parity from a prompt template or new badges.
